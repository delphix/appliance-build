# SBOM Generation — appliance-build Merge Design (Phase 3)

- **Date:** 2026-09-15
- **Status:** Design / feasibility (pending review)
- **Epic:** [CP-13455](https://perforce.atlassian.net/browse/CP-13455) — CycloneDX SBOM for Delphix engine product images
- **Story:** [CP-13466](https://perforce.atlassian.net/browse/CP-13466) — appliance-build: merge 1st-party package SBOMs into the per-image BOM
- **Parent design docs:** `docs/specs/2026-06-15-sbom-generation-design.md` (epic-level design), `docs/specs/2026-06-23-sbom-generation-implementation-plan.md` (phase sequencing)
- **Repos affected:** `appliance-build` only

## Goal

Phase 1 (CP-13464, merged) produces a flat per-image CycloneDX base document — every
installed `.deb` as a `pkg:deb` component, via a Syft chroot scan. Phase 2 (CP-13465, in
review) produces a per-`.deb` CycloneDX sidecar for each 1st-party `linux-pkg` package
flagged `SBOM_DEEP_SCAN`, uploaded to S3 beside that `.deb`.

This design covers **Phase 3**: extending `appliance-build` to collect the sidecars that
exist for a given image's installed packages and merge each into the Phase 1 base, so a
1st-party deb's bundled third-party composition (jars, npm, Rust crates, …) shows up nested
under its own `pkg:deb` entry instead of that package staying an opaque flat line item.

**Non-goals:**
- Changing CP-13465's sidecar format again.
- Building the DCT/Hyperscale **producer** side (their builds emitting
  `delphix-dct.cdx.json` / `delphix-hyperscale.cdx.json`) — that remains an unstoried,
  deferred item under CP-13455. This design *does* build the consumer-side by-name lookup
  for those two components now (see *Scope decision* below), but it will find nothing to
  merge until the producer stories are filed and land.
- The customer-facing publishing switch (CSV → CycloneDX on the download site).
- Decommissioning the legacy `generate_bom`/`combine_bom` CSV pipeline (CP-13468).

## Correction to prior planning docs

Both CP-13466's own Jira description and the epic-level implementation-plan doc
(`2026-06-23-sbom-generation-implementation-plan.md`) describe Phase 2 as producing one
sidecar **per package**: `<package>.cdx.json`. That is no longer accurate. During CP-13465's
review, a reviewer flagged that a package emitting multiple `.deb`s needs a distinct BOM per
`.deb`, not one merged package-level document. The implementation (PR delphix/linux-pkg#418,
as of commit `8923f53`) was changed to a **strict 1:1 `.deb` ↔ `.cdx.json` mapping**: every
built `.deb` gets its own sidecar, named `<deb-filename>.deb.cdx.json`, uploaded beside it in
S3. There is no package-level merge step in `linux-pkg` at all.

This design is written against the **actual** per-`.deb` convention. CP-13466's Jira
description and the implementation-plan doc should be updated to match once this design is
accepted, to avoid a future reader assuming the stale package-level scheme.

Practically, this correction is good news for Phase 3: it resolves the epic design doc's own
open question about "deb → package SBOM association for packages that emit multiple `.deb`s
from one source build" — each `.deb` now has an unambiguous, dedicated sidecar, so there is
no multi-deb ambiguity to resolve at merge time.

## Background: current state of the relevant pieces

**Phase 1's hook** (`live-build/config/hooks/configuration/95-generate-sbom.binary`,
merged) generates the base scan and validates it:

```bash
SYFT_FILE_METADATA_SELECTION=none syft scan dir:binary \
	--select-catalogers dpkg \
	--source-name "$ARTIFACT_NAME" \
	--source-version "$DELPHIX_APPLIANCE_VERSION" \
	-o "cyclonedx-json@1.6=$ARTIFACT_NAME.cdx.json"

cyclonedx-cli validate \
	--input-file "$ARTIFACT_NAME.cdx.json" \
	--input-format json \
	--input-version v1_6 \
	--fail-on-errors
```

This is a `.binary`-suffixed hook, which live-build runs **host-side against the assembled
`binary/` directory**, not chrooted — it already has normal host filesystem and (per prior
experience fixing the validate step) does not require network access, since
`cyclonedx-cli validate` runs entirely offline against a bundled schema.

**`delphix-build-info`** (`scripts/create-build-info-package.sh`) is a `.deb` built once per
build and installed into **every** image. It copies each package's `GIT_HASH`, `BUILD_INFO`,
`PACKAGE_MIRROR_URL_*`, and `metadata.json` (when present) into
`/var/delphix-buildinfo/packages/<pkg>/`, plus copies the top-level `COMPONENTS` and
`KERNEL_VERSIONS` manifests verbatim into `/var/delphix-buildinfo/packages/`. It does **not**
currently copy `.cdx.json` sidecars. Because it's installed into the image, `COMPONENTS` is
available at `binary/var/delphix-buildinfo/packages/COMPONENTS` inside every build's `binary/`
directory at hook time, with no extra fetch — this design relies on that.

**`COMPONENTS`** is a manifest generated by `linux-pkg`'s `combine-packages` job:
`<package-name>:<s3-uri-to-that-package's-artifact-directory>`, one line per `linux-pkg`-built
package (1st-party apps and 3rd-party forks alike — anything `linux-pkg` builds, as opposed to
a stock package installed straight from the Ubuntu apt mirror). `scripts/common.sh`'s
`download_combined_packages_artifacts()` already dereferences it to fetch each package's
artifacts from S3.

**A real gap this design must close:** `scripts/build-ancillary-repository.sh` downloads all
combined-packages artifacts (including any `.cdx.json` sidecars), plus DCT/Hyperscale
artifacts when those variants are being built, into a `mktemp -d` working directory —
and **deletes that directory (`rm -rf "$WORK_DIRECTORY"`) at the end of the same script**,
before `run-live-build.sh` ever runs for any variant/platform combination. Sidecars must be
persisted somewhere durable before this cleanup, or Phase 3 has nothing to merge.

## Scope decision: DCT/Hyperscale lookup

Included now, alongside the `COMPONENTS`-based combined-packages path, even though the
producer side is unstoried. Rationale: the by-name lookup is a small addition with the same
shape as the combined-packages path, it is harmless when it finds nothing, and building it
now avoids a second design/review pass on this same merge logic once the DCT/Hyperscale
producer stories land.

## Architecture

A single new step in `scripts/run-live-build.sh`, inserted **after `lb build` succeeds and
before the existing artifact-move loop** (`for ext in debs.tar.gz $vm_artifact_ext
packages.list cdx.json`). This is the integration point the epic-level design doc originally
specified. At that point, both required inputs are present and host-visible:

- `binary/` — the just-built rootfs, containing `var/lib/dpkg/status` (what's actually
  installed on *this* image) and `var/delphix-buildinfo/packages/COMPONENTS`.
- `$ARTIFACT_NAME.cdx.json` — the base document the `95-generate-sbom.binary` hook already
  produced and validated.

A companion change in `scripts/build-ancillary-repository.sh` persists sidecars before its
temp directory is deleted, to a new directory alongside the existing ancillary repository
output:

```
live-build/build/
├── ancillary-repository/        (existing)
└── sboms/                       (new)
    ├── <linux-pkg-package-name>/
    │   └── <deb-filename>.deb.cdx.json   (one or more per package)
    ├── dct/
    │   └── delphix-dct.cdx.json          (only if DCT variant downloaded)
    └── hyperscale/
        └── delphix-hyperscale.cdx.json   (only if hyperscale variant downloaded)
```

This directory has the same lifetime as `ancillary-repository/` — built once per whole build
invocation, read by every subsequent `run-live-build.sh` call for each variant/platform in
that build.

## Data flow

1. **`build-ancillary-repository.sh`** (existing download calls unchanged) — immediately
   after `download_combined_packages_artifacts` / `download_dct_artifacts` /
   `download_hyperscale_artifacts` populate `$WORK_DIRECTORY/artifacts`, copy every
   `*.cdx.json` found under it into `live-build/build/sboms/` (mirroring the
   `packages/<pkg>/` structure for combined-packages, and flattening `dct/` / `hyperscale/`
   by their fixed filenames) — before the existing `rm -rf "$WORK_DIRECTORY"` runs.

2. **`run-live-build.sh`**, after `lb build` succeeds, before the artifact-move loop:
   - Skip entirely (log and continue to the existing move loop) if `live-build/build/sboms/`
     doesn't exist or is empty — degrades to Phase-1-only behavior.
   - For each sidecar under `live-build/build/sboms/<pkg>/`, parse its filename back into the
     standard Debian `<name>_<version>_<arch>.deb` triple and check whether that exact
     Package+Version+Architecture is present in `binary/var/lib/dpkg/status`. A package
     appearing in the shared `COMPONENTS` manifest is not necessarily installed on *this*
     variant/platform — only debs actually present on this image are candidates.
   - Separately, check whether `delphix-dct` / `delphix-hyperscale` is present in
     `binary/var/lib/dpkg/status`; if so, look for
     `live-build/build/sboms/dct/delphix-dct.cdx.json` /
     `live-build/build/sboms/hyperscale/delphix-hyperscale.cdx.json`.
   - For every match, run `cyclonedx-cli merge` to fold the sidecar into
     `$ARTIFACT_NAME.cdx.json`, nesting its components under the owning `pkg:deb` entry
     (exact CLI invocation/flags for hierarchical nesting to be confirmed against the
     installed `cyclonedx-cli` version — see *Implementation risks*).
   - After all merges, re-run the same `cyclonedx-cli validate` invocation Phase 1 already
     uses, against the final merged document.
3. The existing artifact-move loop and S3 upload are unchanged.

## Error handling

| Condition | Behavior |
|---|---|
| Flagged package's sidecar missing entirely | **Warn** (build-log message), deb stays flat. Not a build failure in this rollout — a linux-pkg-side producer hiccup shouldn't block every appliance-build image. |
| Sidecar present but `cyclonedx-cli merge` or the final `validate` fails | **Fail the build.** A structurally broken sidecar is a data-integrity problem, not a coverage gap — consistent with Phase 1's existing validate-failure behavior. |
| `live-build/build/sboms/` missing or empty | Treat as "no sidecars available anywhere" — degrade to Phase-1-only output, no failure. Covers the case where `build-ancillary-repository.sh` predates this change or genuinely found nothing to persist. |

## Testing

- **Fixture-driven unit test** of the classification/matching logic in isolation (fake
  `dpkg status` content + a fake `live-build/build/sboms/` tree), asserting correct
  merge-candidate selection without invoking real `syft`/`cyclonedx-cli`.
- **Real build, variant with a flagged package installed** — confirm the merged document
  nests that package's deep components under the correct `pkg:deb` entry.
- **Real build, variant with no flagged packages installed** — confirm output is unchanged
  from the Phase-1-only baseline (regression safety net).
- Evidence in the PR follows the epic's existing verification policy: a successful
  appliance-build Jenkins job link, plus the actual contents of the resulting merged
  CycloneDX file.
- **Pre-flight check before implementation starts:** confirm `zfs` and
  `containerized-masking` (both `SBOM_DEEP_SCAN`-flagged) actually appear in a real, current
  `combine-packages` COMPONENTS output. An ad hoc pre-push COMPONENTS listing reviewed during
  this design's discussion was missing both. If that holds against a real `combine-packages`
  run, it is a Phase 2 classification bug blocking Phase 3 — to be fixed in `linux-pkg`, not
  routed around here.

## Implementation risks / open items

- **`cyclonedx-cli merge` exact semantics** (flags for hierarchical nesting vs. flat
  concatenation) need verifying against the actual installed `cyclonedx-cli` version as the
  first implementation task — this design does not assume specific CLI syntax.
- **Stale planning docs:** CP-13466's Jira description and
  `2026-06-23-sbom-generation-implementation-plan.md` both still describe the superseded
  package-level (`<package>.cdx.json`) sidecar scheme — update both once this design is
  accepted.
- **DCT/Hyperscale lookup will be inert** until the deferred producer stories are filed and
  land — expected and intentional, not a bug to chase.
- **Debian filename parsing edge cases** (epoch in version, binNMU-style version suffixes)
  should be validated against real `linux-pkg` package output during implementation, not
  assumed from the common case.
